Build real backend systems using CRUD, relations, filtering, pagination, and clean API design.

Global Rules (Important)

You must first create base entities using CRUD APIs, then use their IDs in business APIs. Everything must be done via HTTP requests. 
1. Create main entities (users, products, courses, etc.)
2. Save returned IDs
3. Use IDs in business APIs (orders, bookings, tickets...)
4. No manual database inserts

NOTE: Global Filtering, Pagination & Sorting (Applies to ALL APIs)

Any API endpoint that returns a list of items must support filtering, pagination, and sorting using query parameters. This rule applies to all projects and all main entities.

This logic is implemented once and reused across all controllers. No frontend logic is involved — everything is handled by backend APIs.

Applies To


GET /api/bookings
GET /api/orders
GET /api/tickets
GET /api/posts
GET /api/students
GET /api/users

Filtering

Any field in the model can be used as a filter using query parameters. 


GET /api/bookings?status=confirmed
GET /api/orders?userId=65fa123abc
GET /api/tickets?priority=high
GET /api/posts?authorId=65fa999xyz

Pagination (Required)

Pagination must be supported on all list endpoints. 


?page=1&limit=10


GET /api/bookings?page=2&limit=5
Default values if not provided:
page = 1   |   limit = 10

Sorting

Sorting is optional and controlled using query parameters. 


?sort=createdAt&order=desc


GET /api/orders?sort=createdAt&order=asc
GET /api/bookings?sort=startDate&order=desc
Default sorting:
sort = createdAt   |   order = desc

Combined Example (Real-Life)


GET /api/orders?
status=delivered
&userId=65fa123abc
&page=1
&limit=5
&sort=createdAt
&order=desc
Do NOT create separate endpoints for filtering or pagination.
Everything must be handled using query parameters on the main GET endpoint.
