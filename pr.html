What is a Pull Request?

A Pull Request (PR) is a mechanism in GitHub to propose changes from one branch to another, typically from a feature branch to the main branch. It allows team members to review, discuss, and approve changes before merging.

Why Use Pull Requests?

  • Code Quality: Peer reviews ensure better code.
  • Collaboration: Discuss changes with the team.
  • History: Maintain a record of discussions and decisions.

In companies, PRs are essential for maintaining stable codebases.

Step 1: Create a Feature Branch

Always work on a separate branch for new features or fixes.

git checkout -b feature/new-feature

This creates and switches to a new branch.

Step 2: Make Changes and Commit

Edit files, then stage and commit your changes.

git add .
git commit -m "Implement new feature"

Use descriptive commit messages.

Step 3: Push the Branch to GitHub

Upload your branch to the remote repository.

git push -u origin feature/new-feature

The -u sets the upstream tracking.

Step 4: Navigate to GitHub and Create PR

Go to your repository on GitHub. You'll see a prompt to create a PR for the recently pushed branch.

Click "Compare & pull request".

Step 5: Fill in PR Details

Provide a title, description, assign reviewers, add labels.

Describe what changes were made and why.

Click "Create pull request".

Step 6: Code Review

Reviewers examine the code, leave comments, suggest changes.

Discuss and resolve issues.

Step 7: Address Feedback

Make necessary changes locally, commit, and push to the same branch.

git add .
git commit -m "Address review comments"
git push

The PR updates automatically.

Step 8: Merge the PR

Once approved and tests pass, merge the PR.

Choose merge method: Create merge commit, Squash and merge, or Rebase and merge.

Workflows in Companies: Feature Branch Workflow

All features developed in isolated branches. PRs used for review before merging to main.

Suitable for continuous delivery.

Workflows in Companies: Gitflow

Uses dev and main branches, with feature, release, hotfix branches.

PRs merge features into dev, releases into main.

Ideal for versioned releases.

Collaboration: Devs work on features, QA tests releases.

Collaboration Between Teams and QA

In companies, PR workflow involves:

  • Dev creates PR after feature complete.
  • Code review by peers.
  • QA performs manual testing on the branch or preview environment.
  • Feedback loop: Fix issues, update PR.
  • Approve and merge once all checks pass.

This ensures quality and shared responsibility.

Best Practices for PRs

  • Keep PRs small and focused.
  • Write clear descriptions and link to issues.
  • Request reviews from relevant people.
  • Respond promptly to feedback.
